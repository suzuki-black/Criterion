# M0 技術検証の記録

指示書 §9 M0 の 4 本の単体テスト ROM の結果をまとめる。数値は openMSX（`My_FS-A1ST_512K`）での値で、
R800 の速度比が実機と異なるため**目安**。確定値は実機で取り直す。

| # | 内容 | ROM | 状態 |
|---|---|---|---|
| 1 | SP2 リングでの 0〜8 ドット/フレーム可変速・逆走 | `build/m0_scroll.rom` | openMSX で検証済み（実機未確認） |
| 2 | 12 帯ラスター＋HR ポーリング帯 | `build/m0_raster.rom` | openMSX で検証済み（実機未確認） |
| 3 | PCM 方式 A/B/C の比較 | `build/m0_pcm.rom` | openMSX で検証済み（実機未確認） |
| 4 | SCREEN 12/5 のモード分割境界 | `build/m0_mode.rom` | openMSX で検証済み（実機未確認） |

## M0-1 横スクロール（SP2 リング）

### 構成

- SCREEN5、R#25 = SP2|MSK、R#2 = 0x3F（ページ 1 指定でページ 0|1 の 512 幅リングを表示）。
- ページ 2 に 8×212 の列ストリップを 32 本生成し、世界の 1 列 = HMMM 1 回（4×212 = 848 バイト）で描き込む。
- スクロールレジスタは VBLANK（H.TIMI）で適用。メインは次フレームの位置計算と列の描き込みだけを行う。
- 描き込み済み範囲 [lo, hi) を管理し、右に 264、左に 8 ドットの余裕を保つ。範囲外へ飛んだらリングを張り直す。
- 速度プログラム: 0.5 → 1 → 2 → 4 → 8 ドット/フレーム、1/2 秒で急停止、逆走 8 ドット/フレーム、停止 の繰り返し。

### 結果（openMSX）

| 項目 | 値 |
|---|---|
| 位置換算 | `R#26 = ((x+7)>>3)&63`, `R#27 = (-x)&7`。x = 0〜9, 15, 248, 255〜257, 300, 504, 511〜513, 1000, 4093, 65530 の 23 位置で画素完全一致 |
| フレームの遅れ | 速度プログラム 972 フレーム（約 16 秒。8 ドット/フレーム・急停止・逆走を含む）で 0（絶対時刻同期 `frame_sync` で計数） |
| CPU 残量（最悪） | アイドル 574 / 基準 850 ≒ 68%（8 ドット/フレーム時。列の HMMM 完了待ちを含む） |
| 1 列の描き込み | 8 ドット/フレーム時に 1 フレーム 1 列。1 列（HMMM 848 バイト）で 1 フレームの約 1/3 を使う。4 列は 1 フレームに収まらない |
| コード量 | 約 2KB（`--max-allocs-per-node 9000`） |

### 分かったこと

- 最初はフレーム待ちが「処理のあとで次の VBLANK まで待つ」形（前作で 20fps に落ちた形）だった。絶対時刻同期へ
  直したところ、**起動直後に 7 フレームの遅れ**が見えた（初期のリング充填を 1 フレーム 4 列ずつ行っていた）。
  旧方式の計測はこれを数えていなかった。表示前にリングを埋め切るよう修正し、遅れは 0。

- SCREEN5 の色 0 は既定で透明で、R#7（枠線色）が背景に透ける。負荷表示に R#7 を使うなら R#8 の TP ビットが必須。
- CPU 残量の低下は、ほぼ列の HMMM 完了待ち。本番では完了待ちの間にゲームロジックを進めれば取り戻せる。
- 未確認: 実機での見え方と CPU 残量。コードは ROM 上で動いている（本番は前作同様 RAM 実行にする）。

## M0-2 多段ラスター＋HR ポーリング帯

### 構成

- ラスターリスト（指示書 8.4）をコア `src/core/raster.c` に実装。1 項目 10 バイト、ダブルバッファ。
  メインが裏の表を組んで `ras_commit`、VBLANK 割込みが表を差し替えて先頭（line 0）を適用し、最初の R#19 を仕込む。
- 画面: 0〜15 行 = 表示帯（固定）、16〜163 行 = N 本の帯（2〜16。帯ごとに別速度・別方向の横スクロール＋目印色）、
  164〜211 行 = 陽炎帯（HR ポーリングで毎ライン横位置を正弦波で変える）。
- 割込みの入口を 2 方式で比較:
  - **BIOS 方式**: BIOS の割込みハンドラ → H.KEYI（前作と同じ）。
  - **直接方式**: ページ 0 を RAM に切り替えて 0x0038 で直接受ける。BIOS を経由しない（JIFFY は自前で進める）。
- 起動時にページ 1〜2 を RAM へ複製して RAM から実行する（`sys_ram_exec`。指示書 8.1）。
- ISR の間は枠線を黄色にする（指示書 8.13 の負荷可視化）。
- 自動検証 `tools/test/run_m0_raster.sh`: 方式 × 陽炎 × 帯の本数を総当たりし、時間を止めた画面で
  帯の境界・帯ごとの横位置・陽炎の各行を画素照合する（`check_raster.py`）。

### 結果（openMSX、RAM 実行、補正 g_ras_bias = 4）

CPU 残量（分割なしを 100 とした平均アイドル）:

| 帯の本数 | 2 | 4 | 6 | 8 | 10 | 12 | 14 | 16 |
|---|---|---|---|---|---|---|---|---|
| 直接方式・陽炎なし | 94 | 91 | 87 | 83 | 79 | **75** | 71 | 67 |
| 直接方式・陽炎あり（R#27 のみ・48 ライン） | 64 | 61 | 57 | 53 | 49 | **45** | 41 | 37 |
| BIOS 方式・陽炎なし | 94 | 89 | 85 | 81 | 77 | 73 | 68 | 65 |

- 直接方式は全設定でフレームの遅れ 0、帯の境界のずれ 0〜−1 行、陽炎帯は 47〜48/48 行が期待どおり。
  **16 帯（間隔 9 行）まで成立**（openMSX）。分割 1 本あたりの CPU は約 2%。
- 帯の境界の行は、レジスタがラインの途中で書き換わるので 1 行ほど崩れる（横位置 NG 行 ≒ 境界 1 本あたり 1〜2 行）。
  指示書 8.4 の「境界は黒い線で隠す」規約で吸収する。
- RAM 実行で、何もしないときのループの速さが ROM 実行の約 2.7 倍（基準アイドル 842 → 2242〜2252）。

### 分かったこと

- **陽炎帯の毎ライン書き換えは R#27 だけ**（帰線期間での書き込み 1 回）。R#26＋R#27 の 2 回は、間接レジスタ（R#17）で
  帰線期間の書き込みを最小にしても、2 回目が表示の左 20〜40 ドットにかかって行が割れる。振幅は R#27 の 0〜7 ドット。
  大きなうねりは帯単位（割込み）で作る。指示書 5.4 の設計（R#27 を正弦波で）どおり。
- **BIOS 方式は、長い割込み処理が VBLANK 際まで延びると VBLANK を取りこぼす**。BIOS が割込みから戻った直後に
  S#0 を読んで VBLANK フラグを消すので、自前の「表の仕込み直し」が走らず、**1 フレームおきに帯が全部消える**。
  直接方式は割込みを自分で受けるので起きない → **エンジンは直接方式を標準にする**。
- 割込みハンドラのレジスタ約束違反を 1 件踏んだ。陽炎帯の処理で `outi` 用に C を 0x9B にして戻り、呼び出し元が C を
  S#0（bit7 = VBLANK）として見ていたため、陽炎帯の終わりを毎フレーム VBLANK と誤判定していた。
  ブレークポイントで ISR 入口の R#15/R#19/B/C を記録して特定した。
- 起動時の全画面消去（HMMV）の完了を待たずに CPU で背景を描き、追いついた消去に先頭行を消されていた（`vdp_cmd_wait` を追加）。

### M0-3 での変更の影響

M0-3 で割込みハンドラを軽くした（直接方式で R#15 を常に 1、FH の判定を IN 1 回）結果、直接方式の CPU 残量は
12 帯で 75% → 78%、12 帯＋陽炎帯で 45% → 48% に上がった。帯の境界は一律 1 行早まり（ずれ −1 行）、
補正は 3 のほうが合う可能性がある（実機で決める）。

### 実機で確かめること

`build/m0_raster.rom` の操作: ←→ 帯の本数 / SPACE 陽炎帯（切 → R#26+R#27 → R#27 のみ）/ ↑ 直接方式 / ↓ BIOS 方式 /
INS・DEL 補正（bias）±1。画面上部に方式・帯の本数・CPU 残量（IDLE）・遅れ（LATE）・補正値が出る。

1. 直接方式で、帯 12 本・16 本が崩れずに出るか（前作の BIOS 方式の実測上限は 8 本・間隔 22 行）。
2. 帯の境界が期待の行に来る補正値（openMSX では 4）。
3. 陽炎帯 R#27 のみで行が割れないか。R#26＋R#27 で割れるか（openMSX では割れる）。
4. CPU 残量（IDLE）の実機値。

## M0-3 PCM 方式 A/B/C の比較

### 構成

- 負荷: M0-1 のスクロール（速度プログラム: 0.5→8 ドット/フレーム・急停止・逆走、列の描き込み）＋ M0-2 の 12 帯
  （帯ごとの視差のずれ）＋ 陽炎帯（R#27 のみ、48 ライン。切替）。その上で試験音をループ再生する。
- 試験音: `tools/gen_pcm.py` で合成したオーケストラヒット風の長調和音（0.4 秒、7867Hz = 2 ラインに 1 サンプル、8 ビット）。
  既存のサンプルは使っていない（指示書 6.4）。
- 方式 A/C は `src/core/raster.c`（走査線割込みに相乗り）、方式 B は `src/core/pcmb.c`（S1990 タイマを待ちループで見る）。
- 計測 `tools/test/run_m0_pcm.sh`: D/A ポート（0xA4）への全書き込みの時刻を openMSX のウォッチポイントで記録し、
  間隔のばらつき・欠けを集計（`check_pcm.py`）。各方式の録音も取る。

### 結果（openMSX、2 秒間。理想は 7867 回/秒、間隔 127.1us）

| 方式 | 陽炎帯 | CPU 残量 | 出力数/秒 | 間隔の標準偏差 | 最大間隔 | 理想から ±25% 外 |
|---|---|---|---|---|---|---|
| PCM なし | なし / あり | 85% / 54% | — | — | — | — |
| A | なし | 36% | 7370 | 93us | 1174us（毎フレーム 18 ラインの穴） | 1.0% |
| A | あり | 25% | 5870 | 330us | 3259us（陽炎帯の 51 ライン） | 3.5% |
| B | なし | 23%※ | 7160 | 138us | 1834us | 20.3% |
| B | あり | 16%※ | 4435 | 594us | 4180us | 28.0% |
| **C** | なし | **42%** | **7850** | **5.8us** | **170us** | **1.2%** |
| **C** | あり | **20%** | **7850** | **16us** | **245us** | **4.9%** |

※ 方式 B の CPU 残量は、ポーリング自体が待ちループの中で走るため実際より低く出る（目安にならない）。

**決定: 方式 C**（指示書の推奨どおり）。A は毎フレームの穴（246〜261 行）と HR ポーリング帯の間が欠けて音が伸び、
B は割込み処理（帯・陽炎帯）やメインの重い区間で止まる。C だけが理想の速さで、ばらつきもほぼ無い。
課題は CPU で、方式 C の 1 刻み（2 ライン）あたり約 50us かかっている（12 帯＋スクロールで 85% → 42%）。
VDP へのアクセスが 1 刻み 3 回（S#1 読み、R#19 書き 2 回）で約 26us は削れないので、下限は 20% 前後。
残りは割込み処理の命令数なので、M1 で刻み専用の短い経路に詰める。

### 分かったこと（エンジンの設計に効くもの）

1. **turboR の R800 は VDP への I/O 1 回に 8.6us かかる**（62 クロック。1 ラインに 7 回ほど）。PCM ポート（0xA4）と
   S1990 タイマ（0xE6/E7）は 1.6us、NOP は 0.14us（探り ROM `build/m0_probe.rom` で実測、openMSX）。
   割込み処理の速さは VDP アクセスの回数でほぼ決まる。陽炎帯で R#26＋R#27 が帰線期間に収まらなかった理由もこれ。
2. **走査線割込みは R#19 = 0〜244 でしか起きない**（246〜255 は起きない。VBLANK の後も 244 までは起きる）。
   1 フレームの割込みの順番は 212, 214, …, 244, (穴), 0, 2, …, 210。
3. **PCM の 15.7kHz カウンタ（0xA4 の読み）は D/A に書くたびに 0 に戻る**ので、経過時間の計測には使えない。
   計測には S1990 のフリーランタイマ（1 カウント 3.91us、1 ライン 16.27 カウント）を使う。
4. **刻み方式**: PCM 再生中は割込みを 2 ラインごとの固定の刻みにし、**入ったら何よりも先に次の刻みを仕込む**。
   ラスターの項目はその刻みまでに来ているものを適用する（最大 1 ライン早まる。境界は黒線で隠す規約で吸収）。
   サンプルとラスターを別々の事象として「近い方を仕込む」作りは、重なった割込みで次の仕込みが遅れ、
   1 フレーム丸ごと止まった（2 秒に 30 回強）。「過ぎていたら今出す」追いつき判定も試したが、時間の見積もりが
   ずれて不安定だったので捨てた。
5. **刻み方式では VBLANK 割込みを止め、VBLANK の仕事は刻み 212 の中で行う**。VBLANK 割込みと刻みの前後は
   条件しだいで入れ替わり（陽炎帯の有無で変わった）、VBLANK の処理（1.4 ライン）で次の刻みを取りこぼした。
   万一刻みが途切れたら、メインのフレーム待ちの見張り（S1990 タイマで約 35ms）が VBLANK 割込みを戻して張り直す。
6. **R#19 = r の割込みは表示ライン r + 3 あたりで来る**（補正 g_ras_bias = 4 と同じずれ）。HR ポーリング帯は刻みより
   3 ライン後ろで終わるので、帯の後は 1 つ先の刻みを仕込む。
7. **メインの割込み禁止は 1 ライン未満に**。VDP コマンドの発行（R#32〜46 の 15 本）を一度に書くと 2.3 ライン割込みが
   止まり、刻みを取りこぼした。5 本ずつ 3 回に分けた（`vdp.c` の `cmd_flush`）。
8. 鳴らし続けるには、割込み側に「次のデータ」の予約枠が要る（`pcm_queue`）。メインが 1 フレームに 1 回差し替えると
   つなぎ目で最大 1 フレーム途切れる。
9. D/A の設定（0xA5）は openMSX の実装に合わせて bit1（MUTE 解除）だけ立てた。**実機資料での確認が必要**（指示書 8.6）。

### 実機で確かめること

`build/m0_pcm.rom` の操作: 0 = PCM なし / 1 = 方式 A / 2 = 方式 B / 3 = 方式 C / SPACE = 陽炎帯 on/off。
起動時は方式 C・陽炎帯あり。

1. 方式 C で音が途切れず、濁らないか（A と B は欠ける・濁るのが期待どおり）。
2. 音が鳴らない場合は D/A の設定（0xA5）の見直しが要る。
3. 画面の帯と陽炎帯が PCM なしのときと同じに見えるか。

## M0-4 SCREEN 12 / SCREEN 5 の画面分割

### 構成

- 上の帯（0〜n−1 行、n = 48: 6 面 / 64: タイトル）を SCREEN 12（GRAPHIC7 + YJK）、下（n〜211 行）を SCREEN 5 にし、
  ラスターリストの「レジスタ列」項目（`RAS_REGS`）で R#0（モード）、R#25（YJK / SP2 / MSK）、R#2（表示ページ）、
  R#8（スプライト表示の可否）、R#26/R#27（横スクロール）を書き換える。
- 上の帯には YJK で合成した自然画風の絵（輝度の縦グラデーション、色相の横変化、地平線）を置き、4 フレームに
  1 ドット横スクロールする。下は M0-1 の世界をスクロールする。スプライト 8 枚を境界をまたいで上下させる。
- 自動検証 `tools/test/run_m0_mode.sh`: 分割の行 × 書き換えの順 × PCM（方式 C）の有無で時間を止めて撮り、
  上の帯は「全面 SCREEN 12」、下の帯は「全面 SCREEN 5」の同じ行と照合する（`check_mode.py`）。

### 結果（openMSX）

| 分割の行 | 書き換えの順 | PCM なし | PCM あり |
|---|---|---|---|
| 48 | 0（R#8 から） | 45〜47 行が乱れる | 46〜47 行 |
| 48 | 1（R#0 から） | 46〜47 行 | 46〜47 行 |
| 64 | 0 | 62〜63 行 | 62〜63 行 |
| 64 | 1 | 61〜63 行 | 62〜63 行 |

- **乱れるのは境界の直前 2〜3 行だけ**（切り替えが補正のぶん早めに始まり、レジスタ 7 本の書き込みに約 1 ライン
  かかる）。帯の内側は全行一致。書き換えの順による差はほぼ無い。→ **上の帯の最下 3 行を黒にする**（絵の規約）。
- スプライトは上の帯では SPD で消え、下の帯では正しく出る（境界をまたぐスプライトは境界で切れる）。
- YJK の帯の横スクロール（SP2 なしの 256 幅、R#26/R#27）: 1 ドット単位で単純にずれ、色化けしない（YJK の色の
  組は VRAM 側の 4 画素単位）。例外は左端のマスクの隣の最初の 4 画素の組だけ（openMSX。**実機は要確認**）。
- 刻みの途切れ 0、フレームの遅れ 0。

### 分かったこと（エンジンの設計に効くもの）

1. **GRAPHIC7（SCREEN 8/12）の表示は VRAM を 2 つの 64KB バンクに 1 バイトずつ交互に読む**（表示アドレス A →
   物理 (A>>1) | ((A&1)<<16)）。SCREEN 5 の単位では、上の帯 n 行は「ページ 0 の 0..n−1 行（偶数バイト）」と
   「ページ 2 の 0..n−1 行（奇数バイト）」を使う。SCREEN 5 のまま一直線に書いた YJK の絵は、半分が別のページを読んだ。
   → 下の帯のリングはページ 0|1（R#2 = 0x3F）、列は n 行目以降だけ描く。列ストリップはページ 3、スプライトは
   ページ 1 の表示外（224 行以降）。
2. **GRAPHIC7 を表示している間は、CPU の VRAM アクセスにもインターリーブの変換がかかり、VDP コマンドの座標の
   解釈も変わる**。分割画面で上の帯の表示中に書いた絵と列の描き込みが壊れた。
   → **VRAM を触ってよいのは SCREEN 5 を表示している区間だけ**。上の帯への切り替えは VBLANK ではなく 244 行
   （R#19 = 240）まで遅らせ、下の帯への切り替え（n 行）に合図（`RAS_MARK`）を付けて、メインはそれを待ってから
   書く（244 行までに終える）。描き直しの間は全面 SCREEN 5 にする。
3. **PCM の刻み 244 は軽く保つ**。刻み 244 は穴埋め（16 ライン）をするので、そこに画面モードの切り替え（約 2 ライン）
   を置くと穴埋めの終わりが後ろへずれ、刻み 0 の処理が遅れて刻み 2 を仕込み損ね、刻みの鎖が 1 フレームおきに切れた。
   刻み 244 の中では項目の適用を先、穴埋めを最後にし、上の帯への切り替えは 244 行（刻み 240）に置いた。
4. 画面モードを書き換えた後は R#19 を書き直す（openMSX でモードの変更が走査線割込みの予定に影響する疑い。
   直接の原因は 3 だったが、書き直しは安全側として残した）。
5. 分割画面のメインループは境界の合図に位相が揃うので、合図を受けた時点でフレーム待ちの基準を置き直す
   （しないと毎フレーム「遅れ」扱いのまま即座に抜け続ける。60fps では回るが待ちが VBLANK に揃わない）。

### 実機で確かめること

`build/m0_mode.rom` の操作: 0 = 全面 SCREEN 5 / 1 = 分割 / 2 = 全面 SCREEN 12 / ←→ = 分割の行 48・64 /
SPACE = 書き換えの順 / P = PCM 方式 C。

1. 境界で乱れる行数（openMSX では 2〜3 行）と、乱れ方（色・横ずれ・ちらつき）。
2. 上の帯の YJK の絵が正しい色で出るか。横スクロールで色化けしないか（openMSX では左端の 4 画素だけ）。
3. 上の帯でスプライトが消え、下の帯で正しく出るか。

## M0 のまとめ（M1 へ持ち越す決定）

| 項目 | 決定 | 根拠 |
|---|---|---|
| 横スクロール | SP2 リング（512 幅）、列単位の HMMM。位置 → R#26/R#27 の換算式 | M0-1 |
| 割込み | 直接方式（ページ 0 RAM の 0x0038、R#15 は常に 1） | M0-2（BIOS 方式は VBLANK を取りこぼす） |
| 帯の本数 | 16 帯（間隔 9 行）まで成立 | M0-2（openMSX） |
| 毎ラインの横揺れ | R#27 だけ | M0-2 |
| PCM | 方式 C（刻み方式） | M0-3 |
| モード分割 | 上の帯 → 244 行で切り替え、VRAM は下の帯の表示中だけ、境界の直前 3 行は黒 | M0-4 |
| 実行場所 | 毎フレームのコードは RAM（sys_ram_exec。M1 ではバンク切替のため前作の動的切替へ） | M0-2 |

実機での確認が残っている点: 帯の補正値（openMSX では 4、軽量化後は 3 が合う可能性）、帯の本数の上限、
VDP の I/O 時間、PCM の D/A 設定（0xA5）、モード分割の乱れ方、YJK の横スクロールの色。
