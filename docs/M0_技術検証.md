## M0-1 横スクロール（SP2 リング）

### 構成

- SCREEN5、R#25 = SP2|MSK、R#2 = 0x3F（ページ 1 指定でページ 0|1 の 512 幅リングを表示）。
- ページ 2 に 8×212 の列ストリップを 32 本生成し、世界の 1 列 = HMMM 1 回（4×212 = 848 バイト）で描き込む。
- スクロールレジスタは VBLANK（H.TIMI）で適用。メインは次フレームの位置計算と列の描き込みだけを行う。
- 描き込み済み範囲 [lo, hi) を管理し、右に 264、左に 8 ドットの余裕を保つ。範囲外へ飛んだらリングを張り直す。
- 速度プログラム: 0.5 → 1 → 2 → 4 → 8 ドット/フレーム、1/2 秒で急停止、逆走 8 ドット/フレーム、停止 の繰り返し。

### 結果（openMSX）

| 項目 | 値 |
|---|---|
| 位置換算 | `R#26 = ((x+7)>>3)&63`, `R#27 = (-x)&7`。x = 0〜9, 15, 248, 255〜257, 300, 504, 511〜513, 1000, 4093, 65530 の 23 位置で画素完全一致 |
| フレームの遅れ | 速度プログラム 972 フレーム（約 16 秒。8 ドット/フレーム・急停止・逆走を含む）で 0（絶対時刻同期 `frame_sync` で計数） |
| CPU 残量（最悪） | アイドル 574 / 基準 850 ≒ 68%（8 ドット/フレーム時。列の HMMM 完了待ちを含む） |
| 1 列の描き込み | 8 ドット/フレーム時に 1 フレーム 1 列。1 列（HMMM 848 バイト）で 1 フレームの約 1/3 を使う。4 列は 1 フレームに収まらない |
| コード量 | 約 2KB（`--max-allocs-per-node 9000`） |

### 分かったこと

- 最初はフレーム待ちが「処理のあとで次の VBLANK まで待つ」形（前作で 20fps に落ちた形）だった。絶対時刻同期へ
  直したところ、**起動直後に 7 フレームの遅れ**が見えた（初期のリング充填を 1 フレーム 4 列ずつ行っていた）。
  旧方式の計測はこれを数えていなかった。表示前にリングを埋め切るよう修正し、遅れは 0。

- SCREEN5 の色 0 は既定で透明で、R#7（枠線色）が背景に透ける。負荷表示に R#7 を使うなら R#8 の TP ビットが必須。
- CPU 残量の低下は、ほぼ列の HMMM 完了待ち。本番では完了待ちの間にゲームロジックを進めれば取り戻せる。
- 未確認: 実機での見え方と CPU 残量。コードは ROM 上で動いている（本番は前作同様 RAM 実行にする）。

## M0-2 多段ラスター＋HR ポーリング帯

### 構成

- ラスターリスト（指示書 8.4）をコア `src/core/raster.c` に実装。1 項目 10 バイト、ダブルバッファ。
  メインが裏の表を組んで `ras_commit`、VBLANK 割込みが表を差し替えて先頭（line 0）を適用し、最初の R#19 を仕込む。
- 画面: 0〜15 行 = 表示帯（固定）、16〜163 行 = N 本の帯（2〜16。帯ごとに別速度・別方向の横スクロール＋目印色）、
  164〜211 行 = 陽炎帯（HR ポーリングで毎ライン横位置を正弦波で変える）。
- 割込みの入口を 2 方式で比較:
  - **BIOS 方式**: BIOS の割込みハンドラ → H.KEYI（前作と同じ）。
  - **直接方式**: ページ 0 を RAM に切り替えて 0x0038 で直接受ける。BIOS を経由しない（JIFFY は自前で進める）。
- 起動時にページ 1〜2 を RAM へ複製して RAM から実行する（`sys_ram_exec`。指示書 8.1）。
- ISR の間は枠線を黄色にする（指示書 8.13 の負荷可視化）。
- 自動検証 `tools/test/run_m0_raster.sh`: 方式 × 陽炎 × 帯の本数を総当たりし、時間を止めた画面で
  帯の境界・帯ごとの横位置・陽炎の各行を画素照合する（`check_raster.py`）。

### 結果（openMSX、RAM 実行、補正 g_ras_bias = 4）

CPU 残量（分割なしを 100 とした平均アイドル）:

| 帯の本数 | 2 | 4 | 6 | 8 | 10 | 12 | 14 | 16 |
|---|---|---|---|---|---|---|---|---|
| 直接方式・陽炎なし | 94 | 91 | 87 | 83 | 79 | **75** | 71 | 67 |
| 直接方式・陽炎あり（R#27 のみ・48 ライン） | 64 | 61 | 57 | 53 | 49 | **45** | 41 | 37 |
| BIOS 方式・陽炎なし | 94 | 89 | 85 | 81 | 77 | 73 | 68 | 65 |

- 直接方式は全設定でフレームの遅れ 0、帯の境界のずれ 0〜−1 行、陽炎帯は 47〜48/48 行が期待どおり。
  **16 帯（間隔 9 行）まで成立**（openMSX）。分割 1 本あたりの CPU は約 2%。
- 帯の境界の行は、レジスタがラインの途中で書き換わるので 1 行ほど崩れる（横位置 NG 行 ≒ 境界 1 本あたり 1〜2 行）。
  指示書 8.4 の「境界は黒い線で隠す」規約で吸収する。
- RAM 実行で、何もしないときのループの速さが ROM 実行の約 2.7 倍（基準アイドル 842 → 2242〜2252）。

### 分かったこと

- **陽炎帯の毎ライン書き換えは R#27 だけ**（帰線期間での書き込み 1 回）。R#26＋R#27 の 2 回は、間接レジスタ（R#17）で
  帰線期間の書き込みを最小にしても、2 回目が表示の左 20〜40 ドットにかかって行が割れる。振幅は R#27 の 0〜7 ドット。
  大きなうねりは帯単位（割込み）で作る。指示書 5.4 の設計（R#27 を正弦波で）どおり。
- **BIOS 方式は、長い割込み処理が VBLANK 際まで延びると VBLANK を取りこぼす**。BIOS が割込みから戻った直後に
  S#0 を読んで VBLANK フラグを消すので、自前の「表の仕込み直し」が走らず、**1 フレームおきに帯が全部消える**。
  直接方式は割込みを自分で受けるので起きない → **エンジンは直接方式を標準にする**。
- 割込みハンドラのレジスタ約束違反を 1 件踏んだ。陽炎帯の処理で `outi` 用に C を 0x9B にして戻り、呼び出し元が C を
  S#0（bit7 = VBLANK）として見ていたため、陽炎帯の終わりを毎フレーム VBLANK と誤判定していた。
  ブレークポイントで ISR 入口の R#15/R#19/B/C を記録して特定した。
- 起動時の全画面消去（HMMV）の完了を待たずに CPU で背景を描き、追いついた消去に先頭行を消されていた（`vdp_cmd_wait` を追加）。

INS・DEL 補正（bias）±1。画面上部に方式・帯の本数・CPU 残量（IDLE）・遅れ（LATE）・補正値が出る。

2. 帯の境界が期待の行に来る補正値（openMSX では 4）。
3. 陽炎帯 R#27 のみで行が割れないか。R#26＋R#27 で割れるか（openMSX では割れる）。
4. CPU 残量（IDLE）の実機値。
